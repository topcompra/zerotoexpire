# ZeroToExpire Web Backend Architecture

## 1. Objective

Extend the existing ZeroToExpire native system to support a browser-based client without duplicating the trading engine, market-data logic, analytics, or state-management layer.

The web application should be treated as an additional presentation target for the existing C++ core.

The target architecture is:

```text
Native C++ Engine
        │
        ├── Qt/QML / Scene Graph → Desktop
        │
        └── Stable Web Snapshot ABI
                    │
                  mmap
                    │
                FastAPI
                    │
              HTTPS / WSS
                    │
             Browser / WebGL
```

The primary architectural rule is:

> **C++ remains the source of truth. FastAPI is a thin transport and web-services layer.**

---

# 2. Design Principles

## 2.1 Do not duplicate the engine

The web backend should not independently calculate:

* options analytics
* GEX
* skew
* market state
* strategy state
* account state
* alerts
* execution state
* AI consensus state
* scanner calculations
* derived market metrics

These should continue to be generated by the native system.

FastAPI consumes already-computed native state.

---

## 2.2 Separate compute from presentation

The C++ core should know nothing about:

* HTML
* CSS
* WebGL
* browser sessions
* HTTP
* REST
* WebSockets
* authentication implementation
* frontend routing

Likewise, the browser should not understand internal C++ implementation structures.

A stable boundary should exist between them.

---

# 4. Native C++ Core

The existing native engine remains authoritative.

The web project should avoid changing the fundamental processing architecture simply to accommodate the browser.

Existing components such as:

```text
stream
 ↓
native calculations
 ↓
native application state
 ↓
mmap / mailbox publication
```

remain intact.

The web system is attached downstream.

---

# 5. Stable Web Snapshot ABI

Rather than exposing arbitrary internal C++ structures directly to Python, introduce an explicit web-facing ABI.

Example conceptual types:

```cpp
OAWebSnapshotV1
GEXWebSnapshotV1
MacroWebSnapshotV1
AccountWebSnapshotV1
ScannerWebSnapshotV1
```

The web ABI represents data needed for presentation rather than native implementation details.

For example:

```cpp
struct WebSnapshotHeader {
    uint32_t magic;
    uint16_t abi_version;
    uint16_t flags;

    uint64_t sequence;
    uint64_t timestamp_ns;

    uint32_t payload_size;
    uint32_t reserved;
};
```

Each snapshot should preferably contain:

```text
header
metadata
fixed-size data
variable-size arrays / indexed regions where required
```

---

# 6. Sequence-Based Publication

Every published state should contain a monotonically increasing sequence number.

Example:

```text
sequence = 918221
```

Consumer behavior:

```text
current sequence == previous sequence
        │
        └── no update

current sequence != previous sequence
        │
        └── process / transmit update
```

This avoids repeatedly transmitting unchanged state.

Sequence IDs also help diagnose:

* dropped updates
* stale state
* consumer lag
* reconnect behavior
* transport problems

---

# 7. Shared-Memory Strategy

Two implementation approaches are acceptable.

## Phase 1 — Existing mmap consumption

For the first working implementation, FastAPI may consume existing native mmaps where their ABI is already sufficiently stable.

```text
existing native mmap
        ↓
FastAPI
```

Advantages:

* minimal native changes
* fast implementation
* useful for validating the full pipeline

This should be considered an integration phase rather than necessarily the final ABI.

---

## Phase 2 — Dedicated Web mmaps

Preferred long-term architecture:

```text
C++ internal state
        ↓
Web Snapshot Builder
        ↓
dedicated web mmap
        ↓
FastAPI
```

Possible files:

```text
web_oa.mmap
web_gex.mmap
web_macro.mmap
web_account.mmap
web_scanner.mmap
```

This isolates the browser-facing contract from native internal structures.

---

# 8. Why Dedicated Web Snapshots Are Preferred

Internal C++ structures should be allowed to evolve without forcing coordinated changes to:

* FastAPI
* browser JavaScript
* TypeScript definitions
* WebGL renderers

For example:

```text
InternalOAState
```

may change freely.

The external contract:

```text
OAWebSnapshotV1
```

remains stable.

If a breaking change is eventually required:

```text
OAWebSnapshotV1
OAWebSnapshotV2
```

can coexist during migration.

---

# 9. FastAPI Responsibilities

FastAPI should remain intentionally thin.

Its responsibilities are:

* map native shared memory
* detect new snapshots
* validate ABI versions
* expose REST endpoints
* maintain WebSocket connections
* manage client subscriptions
* authenticate users
* authorize access
* serialize messages
* handle reconnects
* expose historical/configuration resources
* provide web-specific API semantics

It should generally **not perform market calculations**.

---

# 10. Persistent mmap Mapping

Shared memory should be opened during gateway initialization.

Avoid:

```text
HTTP request
 ↓
open mmap
 ↓
read
 ↓
close mmap
```

Preferred:

```text
FastAPI process starts
 ↓
map all required native state
 ↓
retain mmap handles
 ↓
serve all connected clients
```

Conceptually:

```python
class NativeState:
    def __init__(self):
        self.oa = map_oa()
        self.gex = map_gex()
        self.macro = map_macro()
        self.account = map_account()
```

All browser sessions then consume these shared views.

---

# 11. REST vs WebSocket Responsibilities

The transport should be divided by update characteristics.

## REST

Use REST for relatively slow-changing or request-driven information.

Possible endpoints:

```text
GET /api/config
GET /api/symbols
GET /api/account
GET /api/calendar/{date}
GET /api/history/{symbol}/{date}
GET /api/scanner/results
GET /api/system/status
```

Other administrative operations may later use:

```text
POST
PUT
DELETE
```

as appropriate.

---

# 12. WebSockets

Live system state should primarily flow through WebSockets.

Example:

```text
wss://host/ws
```

One connection can multiplex multiple logical channels.

Possible channels:

```text
oa
gex
macro
account
alerts
scanner
ai
system
```

Client subscription example:

```json
{
  "type": "subscribe",
  "channels": [
    "oa",
    "gex",
    "account"
  ]
}
```

The gateway then sends only requested streams to that connection.

---

# 13. WebSocket Message Envelope

A common message envelope should be defined.

Conceptually:

```text
channel
message type
ABI/protocol version
sequence
timestamp
payload length
payload
```

Example:

```text
OA
sequence 932812
timestamp ...
payload ...
```

The exact binary layout should be defined later after the initial prototype.

---

# 14. Serialization Strategy

## Development phase

JSON may initially be used because it provides:

* easy inspection
* easy browser debugging
* simple logging
* fast schema iteration

Example:

```json
{
  "channel": "oa",
  "sequence": 932812,
  "symbol": "SPX",
  "price": 6483.12
}
```

JSON is acceptable for proving the architecture.

---

## Production hot path

For high-frequency numerical data, move toward binary WebSocket frames.

Target:

```text
C++ numerical structures
        ↓
mmap
        ↓
FastAPI
        ↓
binary WebSocket
        ↓
ArrayBuffer
        ↓
TypedArray
        ↓
WebGL
```

This minimizes:

* string allocation
* JSON encoding
* JSON parsing
* numeric conversions
* memory duplication

---

# 15. Browser Rendering Architecture

The browser should eventually mirror the architectural philosophy of the desktop renderer.

Desktop:

```text
C++ State
   ↓
QML Scene Graph
   ↓
GPU
```

Web:

```text
C++ State
   ↓
Web Snapshot
   ↓
WebSocket
   ↓
TypedArray
   ↓
WebGL
   ↓
GPU
```

Therefore the web application is not a rewritten trading system.

It is another renderer and interaction layer over the same native engine.

---

# 16. WebGL Responsibilities

WebGL should handle graphical surfaces where native-like responsiveness or high visual density matters.

Likely candidates:

* OA chart
* GEX visualization
* macro charts
* heatmaps
* dense historical plots
* premium curves
* skew charts
* high-frequency overlays

DOM/CSS should remain responsible for UI elements better represented as regular interface components:

* menus
* buttons
* dropdowns
* forms
* navigation
* account metadata
* settings
* tables where DOM behavior is useful

The web application therefore becomes a hybrid:

```text
DOM / CSS
+
WebGL rendering surfaces
```

rather than attempting to render everything with either system.

# 20. Update Cadence

Not every native update necessarily needs to become an immediate browser frame.

The native engine may continue processing at its natural cadence.

The web gateway can publish according to channel requirements.

Example:

```text
Native state
100s / 1000s updates per second where appropriate

        ↓

Web publication

OA       up to display-relevant cadence
GEX      on meaningful change
Account  on state change
Alerts   immediately
Macro    on bar/state change
```

The exact cadence should be measured rather than prematurely fixed.

The browser's visual refresh rate ultimately places a practical ceiling on useful visual updates.

---

# 21. Backpressure

Web clients must not be allowed to slow the native system.

The architecture should favor latest-state semantics for visual streams.

If the browser cannot consume:

```text
sequence 100
101
102
103
104
```

fast enough, it is often preferable to deliver:

```text
104
```

instead of building a large queue.

For state visualization:

> **Freshness is usually more important than delivering every intermediate frame.**

Event streams such as executions or alerts may require different semantics and should not automatically discard intermediate events.

---

# 22. State vs Event Channels

The transport should distinguish two categories.

## State

Examples:

* current OA surface
* current GEX
* current account
* current macro state

State can usually use latest-value semantics.

```text
old state can be discarded
```

## Events

Examples:

* alert generated
* order submitted
* order filled
* execution rejected
* system fault

Events may require guaranteed ordering and retention.

This distinction should be explicit in the protocol.

---

# 23. Authentication and Security Boundary

The browser must never gain direct access to native shared memory.

The security boundary is:

```text
Browser
   │
HTTPS / WSS
   │
FastAPI
   │
local IPC
   │
C++
```

FastAPI therefore acts as the externally exposed boundary.

The native engine can remain inaccessible from the public network.

---

# 24. Trading Actions

Read-only web functionality should be implemented before remote trading controls.

If remote execution is later enabled, command flow should remain asymmetric:

```text
Browser
   ↓
authenticated command
   ↓
FastAPI
   ↓
strict native command ABI
   ↓
C++ execution engine
```

FastAPI should not itself become the execution engine.

The native application should validate commands again regardless of validation already performed at the web layer.

---

# 25. Historical Data

Historical resources do not necessarily need to pass through live mmaps.

FastAPI can expose historical data through endpoints backed by the existing canonical storage system.

Example:

```text
GET /api/history/SPX/2026-08-18
```

Potential sources:

* native history files
* Parquet
* binary canonical storage
* indexed cache
* dedicated historical service

The exact storage implementation remains separate from the live-state protocol.

---

# 26. Failure Isolation

Each layer should remain independently restartable where practical.

Example:

```text
FastAPI crashes
      │
      └── C++ native engine continues

Browser disconnects
      │
      └── FastAPI/native engine continue

WebGL error
      │
      └── native state unaffected
```

This is a major reason to preserve process boundaries.

---

# 27. Initial Implementation Sequence

## Phase 1 — End-to-end proof

Expose one existing mmap.

Recommended first candidate:

```text
OA
```

Build:

```text
C++ mmap
 ↓
FastAPI mmap reader
 ↓
WebSocket
 ↓
browser console
```

No sophisticated UI required.

Goal:

> prove native state reaches the browser correctly.

---

## Phase 2 — Basic browser renderer

Connect the OA feed to the current WebGL prototype.

Pipeline:

```text
C++ OA state
 ↓
FastAPI
 ↓
browser
 ↓
WebGL OA surface
```

---

## Phase 3 — Stable Web ABI

Introduce:

```text
OAWebSnapshotV1
```

rather than depending directly on internal OA mmap structures.

Validate:

* ABI version
* sequence
* timestamp
* state integrity

---

## Phase 4 — Multiplexed WebSocket

Add channels:

```text
OA
GEX
MACRO
ACCOUNT
```

and client subscriptions.

---

## Phase 5 — Binary transport

Move heavy numerical channels from JSON to binary frames where profiling shows value.

---

## Phase 6 — Web application shell

Add:

```text
navigation
account
configuration
symbol selection
dates
historical loading
responsive layouts
```

---

## Phase 7 — Authentication

Introduce production-grade user/session authentication before external exposure.

---

## Phase 8 — Remote actions

Only after the read path is stable should actions such as:

* alerts
* configuration updates
* broker interaction
* execution

be considered.

---

# 28. First Milestone

The first meaningful milestone should be intentionally small:

```text
Native OA state
      ↓
existing mmap
      ↓
FastAPI
      ↓
WebSocket
      ↓
browser
      ↓
WebGL
```

Success criteria:

* OA native process remains unchanged or minimally changed
* gateway maps state once
* browser reconnects safely
* sequence IDs work
* no polling over HTTP for live chart state
* no duplicate market calculations in Python
* rendered browser state matches native state

At this point the architecture has been proven.

---

# 29. Architectural Non-Goals

The initial system should **not** attempt to:

* replace the C++ engine
* port analytics to Python
* make FastAPI the market-data processor
* expose mmaps directly to browsers
* reproduce all desktop functionality immediately
* make every internal native structure public
* optimize binary serialization before measuring JSON
* implement remote trading before the read path is stable

---

# 30. Core Architectural Statement

The intended final architecture can be summarized as:

```text
                 ONE NATIVE ENGINE

                       C++
                        │
              ┌─────────┴─────────┐
              │                   │
              ▼                   ▼
         Qt/QML Renderer     Web Snapshot ABI
              │                   │
              ▼                   ▼
           Desktop              mmap
                                  │
                                  ▼
                               FastAPI
                                  │
                                  ▼
                              WebSocket
                                  │
                                  ▼
                                WebGL
                                  │
                                  ▼
                                 Web
```

The desktop application and website therefore remain two presentation targets for the same underlying system.

This preserves the work already invested in the native architecture while giving the application a clean path toward browser, mobile-browser, and remote access.

---

# 31. Open Design Decisions

These should deliberately remain unresolved until implementation/profiling provides evidence:

* whether existing mmaps are sufficient or dedicated web mmaps are required immediately
* one mmap per subsystem vs one consolidated web state mmap
* binary format
* JSON-to-binary transition point
* WebSocket channel granularity
* exact publish cadence
* snapshot size limits
* compression
* historical data transport format
* browser caching
* deployment topology
* authentication provider
* whether FastAPI stays Python long term
* whether the gateway eventually becomes native
* remote execution capabilities

The skeleton should survive changes to any of these decisions.

---

# 32. Guiding Rule

When deciding where new functionality belongs:

```text
Does it understand markets, trading, analytics,
canonical state or execution?
        │
        └── C++

Does it understand users, HTTP, browser sessions,
subscriptions or web transport?
        │
        └── FastAPI

Does it understand pixels, interaction, layout
or visualization?
        │
        └── Browser
```

That separation is the core of the design.
